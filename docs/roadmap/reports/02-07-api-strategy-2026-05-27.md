# Phase 02.07 - API Strategy

Date: 2026-05-27

## Summary

Defined the v1 API boundary strategy and fixed one concrete sensitive-write issue: employee invite emails were using `supabase.auth.admin` from a client component.

## API Boundary Classes

Browser Supabase:

- Used by feature repositories for tenant-scoped reads and low-risk writes protected by RLS.
- Examples: inventory, scheduling, tasks, employees, messages, forms, and reports repositories.

Next route handlers:

- Used for server-only or sensitive application operations.
- Examples: onboarding complete, onboarding repair, employee invite email, logs, cron jobs, detectors, and automation suggestions.

Supabase RPC:

- Used for database-owned tenant-safe workflows.
- Examples: company setup, invite creation, membership assertion, dashboard stats, KPI summary, and audit logging RPCs.

Supabase edge functions:

- Used for AI/copilot, learning, account deletion, schedule event, and vendor sync work.
- Must validate bearer auth, tenant scope, CORS, idempotency, and audit/event logging before production enablement.

Future service:

- Reserved for external integration orchestration once queueing, retries, provider sync, and observability outgrow Next route handlers and edge functions.

## Sensitive Write Fix

Before:

- `src/features/employees/components/InviteEmployeePanel.tsx` called `supabase.auth.admin.inviteUserByEmail` in browser code.

After:

- Client gets the current session access token.
- Client posts invite payload to `/api/employees/invite`.
- Server route verifies the bearer token with Supabase admin.
- Server resolves the requester profile, company, and role.
- Server allows only owner/admin/company_admin/manager roles.
- Server inserts or updates a pending invite record for the same company/email.
- Server sends the Supabase invite email with service role.
- Server writes an `audit_log` row for success or email failure.

## Idempotency Rules

Retryable mutations should:

- Accept or derive a stable idempotency key.
- Use upsert/onConflict, status transitions, or lock checks.
- Return existing resources or final state on repeat calls where possible.
- Store requestId or dedupeKey in metadata for support and audit review.

Employee invite route rule:

- Existing unaccepted company/email invite records are updated instead of blindly creating duplicates.

## Audit Rules

Service-role writes should:

- Verify caller identity or cron secret.
- Resolve tenant scope server-side.
- Never trust `companyId` from the browser alone.
- Use deterministic retry/idempotency behavior.
- Write an audit row or domain event for sensitive mutations.
- Return sanitized errors without secrets or service-role details.

Employee invite route audit:

- Writes `employee_invite_sent` on success.
- Writes `employee_invite_email_failed` if Supabase email sending fails.

## Edge Function Follow-Up Risks

Several edge functions still need future hardening before production enablement:

- Some use wildcard CORS.
- Some use service-role keys directly and must prove caller authentication and tenant scope.
- AI/copilot functions should consistently record dedupe keys, action events, and audit logs.
- Schedule/vendor integration functions should add stronger auth and idempotency before public use.

These are documented as future API hardening work rather than hidden.
